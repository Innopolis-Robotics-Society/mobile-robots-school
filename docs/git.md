# Работа с Git и GitHub

Git хранит историю кода: каждое сохранённое состояние можно посмотреть, сравнить с другим и вернуть. GitHub — сайт, где лежит общая копия репозитория, с которой работает вся команда. В Школе через GitHub вы сдаёте результаты: код, видео, README команды.

Если вы ни разу не работали с Git, пройдите этот документ сверху вниз один раз целиком. Дальше пользуйтесь [шпаргалкой](#шпаргалка) и разделом [«Частые проблемы»](#частые-проблемы).

## Установка и настройка

### Установка

| Система | Как поставить |
| --- | --- |
| Windows | [Git for Windows](https://git-scm.com/download/win). При установке оставьте настройки по умолчанию. Команды вводите в программе **Git Bash** |
| macOS | В терминале `xcode-select --install` или `brew install git` |
| Linux (Ubuntu) | `sudo apt install git` |

Проверка: `git --version` выводит номер версии.

### Имя и почта

Git подписывает каждое изменение. Укажите имя и ту же почту, что в аккаунте GitHub:

```bash
git config --global user.name "Имя Фамилия"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
```

### Доступ к GitHub по SSH

GitHub не принимает пароль от аккаунта при работе из терминала. Проще всего один раз настроить SSH-ключ.

1. Создайте ключ (на все вопросы можно нажимать Enter):

   ```bash
   ssh-keygen -t ed25519 -C "you@example.com"
   ```

2. Выведите публичный ключ и скопируйте строку целиком:

   ```bash
   cat ~/.ssh/id_ed25519.pub
   ```

3. На GitHub: **Settings → SSH and GPG keys → New SSH key**, вставьте строку, сохраните.
4. Проверьте: `ssh -T git@github.com` должен поздороваться по вашему нику.

После этого клонируйте репозитории по SSH-ссылке (`git@github.com:...`), а не по HTTPS.

## Репозиторий команды

### Создание

Репозиторий создаёт один человек в команде:

1. Откройте [Организацию](https://github.com/orgs/Innopolis-Robotics-Society/repositories).
2. Нажмите `New repository`
3. Владелец — Innopolis-Robotics-Society, имя — `amr-school26-team-<NAME>`, где <NAME> — имя команды.
4. Нажмите `Create repository`
5. **Settings → Collaborators** — добавьте всех участников команды.


### Клонирование

Каждый участник один раз скачивает репозиторий к себе:

```bash
git clone git@github.com:Innopolis-Robotics-Society/amr-school26-team-<NAME>.git
cd school26-team-N
```

### Что где лежит

Рекомендуем использовать следующую общую структуру

```
school26-team-N/
├── README.md        состав команды, общие сведения
├── firmware/        скетчи, по одной папке на задание
│   └── 03_motor_test/
│       └── 03_motor_test.ino
├── media/           фото и короткие видео для сдачи
└── docs/            таблицы калибровок, графики, схемы подключения, подобранные коэффициенты и углы
```

У Arduino IDE есть правило: **папка скетча называется так же, как файл `.ino` в ней.** Иначе IDE откроет скетч с ошибкой.

## Ежедневная работа

Цикл всегда один и тот же:

```bash
git pull                   # 1. забрать то, что запушили другие
# ... работаете: правите скетч, проверяете на роботе ...
git status                 # 2. посмотреть, что изменилось
git add firmware/03_motor_test
git commit -m "Тест моторов: исправлено направление правого мотора"
git push                   # 3. отправить на GitHub
```

**Начинайте работу с `git pull`.** Большинство проблем в команде случается из-за того, что кто-то работал со старой версией.

### Какие делать коммиты

- **Один коммит — одно законченное изменение.** «Добавлена калибровка датчиков линии» лучше, чем «изменения» с пятью разными правками.
- **Сообщение отвечает на вопрос «что сделано».** Пишите по-русски, коротко: `Подобраны Kp=0.8, Kd=4 для трассы 105a`.
- **Коммитьте рабочий код.** Если скетч не компилируется, не пушьте его в `main`.

## Работа вчетвером: ветки и pull request

Если четыре человека правят один и тот же файл в `main`, рано или поздно они затрут работу друг друга. Поэтому каждое задание делаем в своей ветке, а в `main` оно попадает через pull request после ревью старшего.

```bash
git switch main
git pull
git switch -c line-calibration      # новая ветка под задание
# ... работаете, коммитите ...
git push -u origin line-calibration # первый push ветки
```

Дальше на GitHub появится кнопка **Compare & pull request**:

1. Нажмите её. В описании напишите, что сделано и как проверить, приложите видео или график.
2. В **Reviewers** укажите старшего в команде.
3. Ревьюер смотрит код, оставляет комментарии или одобряет.
4. После одобрения — **Merge pull request**, ветку можно удалить.
5. У себя: `git switch main && git pull`.

## Конфликты

Конфликт — это когда двое изменили одни и те же строки, и Git не знает, чью версию оставить. Выглядит так:

```
<<<<<<< HEAD
const float KP = 0.8;
=======
const float KP = 1.2;
>>>>>>> line-calibration
```

Как разрешить:

1. Откройте файл и решите, какая версия правильная, или объедините обе.
2. Удалите строки-маркеры `<<<<<<<`, `=======`, `>>>>>>>`.
3. Проверьте, что скетч компилируется.
4. `git add <файл>`, затем `git commit`.

Конфликтов меньше, если делать короткие ветки, часто делать `git pull` и договариваться, кто какой файл правит.

## Что не класть в репозиторий

- **Большие видео.** GitHub не принимает файлы больше 100 МБ, а репозиторий с гигабайтами видео неудобно клонировать. Короткие ролики (до 10–20 МБ) кладите в `media/`, длинные — ссылкой в README.
- **Файлы сборки и мусор.** Папки `build/`, `.vscode/`, временные файлы. Перечислите их в `.gitignore`.
- **Пароли, токены, личные данные.**

Пример `.gitignore`:

```
build/
.vscode/
.DS_Store
*.tmp
```

## Шпаргалка

| Что сделать | Команда |
| --- | --- |
| Скачать репозиторий | `git clone <ссылка>` |
| Забрать изменения с GitHub | `git pull` |
| Посмотреть, что изменилось | `git status`, `git diff` |
| Подготовить файлы к коммиту | `git add <файл или папка>` |
| Сохранить изменения | `git commit -m "что сделано"` |
| Отправить на GitHub | `git push` |
| Создать ветку и перейти в неё | `git switch -c <имя>` |
| Перейти в другую ветку | `git switch <имя>` |
| История коммитов | `git log --oneline` |
| Отменить правки в файле (до коммита) | `git restore <файл>` |
| Убрать файл из подготовленных | `git restore --staged <файл>` |

## Частые проблемы

| Что видите | Что случилось | Что делать |
| --- | --- | --- |
| `rejected ... fetch first` при `git push` | На GitHub есть изменения, которых нет у вас | `git pull`, разрешить конфликты, если есть, снова `git push` |
| `Permission denied (publickey)` | SSH-ключ не добавлен на GitHub или клонировали по HTTPS | Пройти раздел про SSH, проверить `ssh -T git@github.com` |
| `Authentication failed` при HTTPS | GitHub не принимает пароль аккаунта | Перейти на SSH: `git remote set-url origin git@github.com:<организация>/<репо>.git` |
| `Please tell me who you are` | Не настроены имя и почта | Команды `git config` из раздела «Имя и почта» |
| Закоммитили лишний файл, ещё не запушили | — | `git reset --soft HEAD~1`, убрать файл, закоммитить заново |
| Закоммитили папку `build/` | Нет `.gitignore` | `git rm -r --cached build/`, добавить `build/` в `.gitignore`, закоммитить |
| `You are in 'detached HEAD' state` | Перешли на коммит, а не на ветку | `git switch main` |
| Arduino IDE не открывает скетч | Имя папки не совпадает с именем `.ino` | Переименовать папку или файл |
| Всё сломалось, непонятно что | — | Ничего не удаляйте. `git status` и `git log --oneline`, скриншот в чат Школы |

## Правки в репозитории Школы

Нашли ошибку в пайбуке или скетче Школы — пришлите исправление:

1. **Fork** репозитория Школы на GitHub.
2. Склонируйте свой форк, создайте ветку, внесите правку, запушьте.
3. Откройте pull request в репозиторий Школы и опишите, что исправили.

Мелкую опечатку можно поправить прямо на сайте GitHub: значок карандаша на странице файла, и GitHub сам сделает форк и pull request.
